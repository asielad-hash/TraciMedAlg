THE STORY
================================================================

Every year, thousands of surgical instruments and sponges are
accidentally left inside patients. The consequences range from
infection to reoperation to death. The root cause is simple:
counting instruments by hand, in a high-stress environment,
with no technological backup.

TrackiMed's ORKing system solves this by placing AI-powered
cameras in the operating room. The system watches the surgical
field in real time, knows exactly which instruments are on the
table, tracks every instrument that moves in or out of the
surgical tray, and raises an alert the moment something goes
missing.

But instrument counting is only the beginning. The same camera
feeds power workflow intelligence — recognizing what phase of
surgery is underway, detecting idle time that inflates costs,
and eventually capturing verbal count calls and medication
administration to cross-check against the visual evidence.

All of this must happen under strict constraints: real-time
performance (under 1 second), absolute patient privacy (every
face blurred before any data is stored), and clinical-grade
accuracy that can withstand regulatory scrutiny for a 510(k)
medical device submission.

This document is the complete operational guide for building,
training, testing, and validating every algorithm component in
the ORKing system.


================================================================
THE TWO INSTRUMENT PROBLEMS
================================================================

There are two fundamentally different vision challenges in the
OR, and they require different algorithmic approaches:

  PROBLEM 1 — THE TABLE (clear view)
  The mayo table and back table hold instruments that are
  visible, separated, and individually identifiable. Here we
  can detect each instrument, draw a pixel-perfect mask around
  it, track its identity across frames, classify what it is,
  and maintain a running count. When something disappears, we
  know exactly what went missing.

  → Solved by: INSTRUMENT TRACKER (#01)

  PROBLEM 2 — THE TRAY (crowded, occluded)
  The instrument tray is a dense pile of metal. Individual
  instruments overlap, reflect light unpredictably, and are
  often impossible to distinguish. We cannot track each one.
  Instead, we watch for EVENTS: a hand reaches in and takes
  something out (TAKE_OUT), or puts something back (PUT_BACK).
  The tray is a black box — we only monitor its boundary.

  → Solved by: TRAY MONITOR (#02)

Together, these two components cover the full instrument
lifecycle: from organized display to crowded storage and back.


================================================================
THE FULL SYSTEM — 6 COMPONENTS
================================================================

  #   COMPONENT              TYPE          STATUS
  ──────────────────────────────────────────────────────
  01  Instrument Tracker     ML            Active
  02  Tray Monitor           ML + Classic  Active
  03  Surgical Workflow      ML + Classic  Active
  04  Camera Controller      Classic       Active
  05  Privacy Engine         Classic + ML  Active
  06  OR Speech              ML            Planned (future)


  01 — INSTRUMENT TRACKER
       Detect, segment, track & count instruments on mayo/back
       table. Instruments are clearly visible and individually
       identifiable. Generates LOST/NEW/BACK count alerts.
       The core safety component — if a sponge goes missing,
       this is what catches it.

  02 — TRAY MONITOR
       Detect instruments taken out / put back into the crowded
       instrument tray. Event-based detection (IN/OUT) — cannot
       individually track inside the tray. Watches for hand-tray
       interactions to infer what happened.

  03 — SURGICAL WORKFLOW
       Two sub-components:
       A) Phase recognition — classify the current surgical phase
          (setup → incision → count → closure → turnover)
       B) Idle detection — find non-operative idle periods where
          no productive work is happening. Feeds directly into
          hospital operations efficiency reporting.

  04 — CAMERA CONTROLLER
       PTZ camera auto-aim in two operational modes:
       A) Table Mode — track mayo/tray table, keep instruments
          in frame. Feed video to #01 and #02.
       B) Room Mode — wide-angle overview of the entire OR.
          Feed video to #03 for workflow detection. Can zoom
          into tables when dedicated cameras are unavailable.

  05 — PRIVACY ENGINE
       Real-time anonymization — the gatekeeper. Every frame
       passes through this FIRST, before any other processing.
       Blurs faces (even with surgical masks and caps), masks
       badge text and monitor screens, scrambles voice identity.
       Hard constraint: < 200ms per frame. No PHI ever persists.

  06 — OR SPEECH (future)
       Transcribe OR speech in real time. Not a standalone
       feature — it feeds critical signals to other engines:
         - Count calls → Instrument Tracker (#01) for count
           verification ("sponge count: ten")
         - Instrument requests → Tray Monitor (#02) to predict
           upcoming TAKE_OUT events ("give me the Kocher")
         - Workflow cues → Surgical Workflow (#03) for phase
           transition hints ("let's do the count")
         - Medication calls → future safety engine
       Development begins when Phase 1 audio data is available.

PER-COMPONENT: WHAT TO DO
================================================================

Each ML component follows: PREPARE → TRAIN → EVALUATE
Each data/ folder has a DATA_README.txt with exact formats.

──────────────────────────────────────────────────────────────
01 — INSTRUMENT TRACKER
──────────────────────────────────────────────────────────────

  WHAT YOU NEED:
    [ ] Anonymized OR videos (mayo/back table view)
    [ ] Base model weights (sam3.pt)
    [ ] Instrument exemplar images (50+ per class)

  STEP 1 — EXTRACT FRAMES:
    python 01_instrument_tracker/data_prep/extract_frames.py \
      --config 01_instrument_tracker/config/config.yaml \
      --video-dir 01_instrument_tracker/data/videos \
      --output-dir 01_instrument_tracker/data/images

  STEP 2 — GENERATE ZERO-SHOT ANNOTATIONS (sam3 env):
    python 01_instrument_tracker/data_prep/generate_zero_shot.py \
      --config 01_instrument_tracker/config/config.yaml \
      --video-dir 01_instrument_tracker/data/videos \
      --output-dir 01_instrument_tracker/data/annotations/zero_shot

  STEP 3 — CONVERT TO COCO (after human review):
    python 01_instrument_tracker/data_prep/convert_to_coco.py \
      --anno-dir 01_instrument_tracker/data/annotations \
      --video-dir 01_instrument_tracker/data/videos \
      --output-dir 01_instrument_tracker/data

  STEP 4 — SPLIT:
    python 01_instrument_tracker/data_prep/prepare_splits.py \
      --config 01_instrument_tracker/config/config.yaml \
      --coco-dir 01_instrument_tracker/data \
      --output-dir 01_instrument_tracker/data

  STEP 5 — EXPORT YOLO FORMAT:
    python 01_instrument_tracker/train/export_yolo_dataset.py \
      --meta-dir 01_instrument_tracker/data/annotations \
      --images-dir 01_instrument_tracker/data/images \
      --output-dir 01_instrument_tracker/data/yolo_dataset

  STEP 6 — TRAIN:
    python 01_instrument_tracker/train/train_detector.py \
      --data-yaml 01_instrument_tracker/data/yolo_dataset/data.yaml \
      --epochs 50 --imgsz 1024

  STEP 7 — EVALUATE:
    python 01_instrument_tracker/eval/evaluate_tracking.py \
      --pred-dir 01_instrument_tracker/data/predictions \
      --gt-dir 01_instrument_tracker/data/ground_truth \
      --config 01_instrument_tracker/config/config.yaml

    python 01_instrument_tracker/eval/evaluate_detection.py \
      --predictions results.json --ground-truth gt.json \
      --config 01_instrument_tracker/config/config.yaml

  TARGETS:
    AUC-ROC >= 0.90 | mIoU >= 0.85 | HOTA >= 0.80
    Count accuracy >= 95% | False alarm rate < 5% | Latency < 1s

================================================================
TRAINING ROADMAP
================================================================

  PHASE 0 — Bootstrap (Q4 2025 – Q1 2026)
    What:  Get the system running with pre-trained models.
    → Instrument Tracker v0.1 (zero-shot, no fine-tune)
    → Privacy Engine validated on test frames
    → Camera Controller calibrated in first OR
    → Gate: functional pipeline, zero-shot demo working

  PHASE 1A — Early Data, 20-50 cases (Q1-Q2 2026)
    What:  First fine-tuned models from Sheba data.
    → Instrument Tracker v0.5 (initial fine-tune on 20-50 cases)
    → Tray Monitor v0.1 (first event detection model)
    → Gate: AUC > 0.75, latency < 1s on OR hardware

  PHASE 1B — Multi-Site, 50-200 cases (Q2-Q3 2026)
    What:  Cross-site validation proves generalization.
    → Instrument Tracker v1.0 (multi-site trained)
    → Tray Monitor v0.5
    → Surgical Workflow v0.1 (first phase detector)
    → Gate: AUC > 0.85, F1 > 0.85, cross-site validated

  PHASE 1C — Full Dataset, 200-1000 cases (Q3-Q4 2026)
    What:  Production-ready models for 510(k) submission.
    → Instrument Tracker v1.5 (production candidate)
    → All components at v1.0
    → Gate: AUC >= 0.90, F1 >= 0.90, 510(k) dataset ready

  PHASE 2 — Workflow Models (Q4 2026 – Q1 2027)
    What:  Workflow intelligence and efficiency reporting.
    → Surgical Workflow v1.0
    → Gate: Phase F1 > 0.88, idle precision > 0.90

  PHASE 3 — Speech & Medication (Q2-Q3 2027)
    What:  Audio intelligence feeds all engines.
    → OR Speech v1.0, Medication Safety Engine
    → Gate: WER <= 10%, count call recognition >= 95%
