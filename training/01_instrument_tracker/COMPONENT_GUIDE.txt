================================================================
01 — INSTRUMENT TRACKER
Component Guide for the Development Team
================================================================


================================================================
THE PROBLEM WE'RE SOLVING
================================================================

Every year, thousands of surgical instruments and sponges are
accidentally left inside patients. The mayo table and back table
hold instruments that are clearly visible and individually
identifiable — this is where our AI watches.

The Instrument Tracker detects each instrument, draws a pixel-
perfect mask around it, tracks its identity across video frames,
classifies what type of instrument it is, and maintains a
running count. The moment something disappears from the table
without being accounted for, the system raises an alert.

This is the core patient safety component of ORKing.


================================================================
WHERE WE ARE TODAY
================================================================

The production system WORKS — zero-shot, no training:

  1. Human annotates keyframes (click on instruments)
  2. SAM3 generates pixel masks at those keyframes
  3. SAM3 propagates masks forward/backward through entire video
  4. Identity-swap correction fixes post-occlusion errors
  5. LOST/NEW/BACK events detected by rule-based state machine
  6. Output: tracked video + per-frame metadata JSON

This runs in the trackInstruments/ web app at localhost:5000.

What's missing: the system doesn't KNOW what it's looking at.
It tracks "object #1" and "object #3" — it doesn't know that
#1 is a sponge and #3 is a Kelly clamp. That knowledge comes
from training on labeled surgical instrument data.


================================================================
HOW INSTRUMENT DATA FLOWS INTO TRAINING
================================================================

The SurgicalInstruments app (separate repo, port 3000) is the
master catalog of all surgical kits and instruments. It contains:

  - Kit definitions (e.g., "Sheba Basic Delicate Set")
  - Instrument inventory per kit (names, counts, categories)
  - Instrument IMAGES and VIDEOS uploaded from sterile processing

This catalog is the SINGLE SOURCE OF TRUTH for:

  1. INSTRUMENT TAXONOMY
     Which instruments exist, how they're named, how they're
     grouped. Training labels come from this catalog.

  2. EXEMPLAR LIBRARY
     Reference images AND video clips of each instrument.
     Both still images and video frames are extracted as
     training data. Videos provide visual diversity (different
     angles, lighting, hands holding the instrument).

  3. KIT VALIDATION
     When we track instruments during surgery, we cross-reference
     against the kit catalog to verify: "this procedure uses the
     Sheba Basic Delicate Set, which should have 42 instruments —
     we see 41 on the table, 1 is missing."

  DATA FLOW:

    SurgicalInstruments App (port 3000)
    (kit catalog + instrument images + videos)
           │
           ├──→ Instrument names + categories
           │    (becomes training labels / class taxonomy)
           │
           ├──→ Instrument images (still photos)
           │    (becomes training images with auto-labels)
           │
           ├──→ Instrument videos (clips)
           │    (frames extracted with jitter for visual diversity)
           │
           ├──→ Kit instrument counts
           │    (becomes ground truth for count validation)
           │
           └──→ Kit definitions + PDF catalogs
                (reference documentation)
           │
           ▼
    run_pipeline.py (ONE COMMAND)
    (collect → deduplicate → label → split → export)
           │
           ▼
    YOLO Dataset (ready to train)
           │
           ▼
    train_detector.py → Trained YOLOv8-seg Model
           │
           ▼
    Production: YOLOv8 detects → SAM3 tracks → count alerts


================================================================
TWO CRITICAL DATA CHALLENGES
================================================================

CHALLENGE 1 — SAME INSTRUMENT, DIFFERENT NAMES ACROSS KITS

  The same physical instrument appears with different names
  in different kit catalogs. For example:

    Kit A: "Richardson Retractor"
    Kit B: "Retractor, Richardson, Loop Handle, 38mm x 38mm"
    Kit C: "Richardson retractor - large"

  These are ALL the same instrument and must be merged into
  ONE training class. If we don't merge them, the model learns
  3 separate classes for 1 object → wastes data and confuses
  the detector.

  HOW WE SOLVE IT:
  The pipeline normalizes instrument names automatically:
    - Lowercase + remove punctuation
    - Remove filler words (the, a, with, for, etc.)
    - Sort remaining tokens alphabetically
    - Group by normalized key

  The dedup log (data/dedup_log.json) shows which names were
  merged so you can review and correct any mistakes.

CHALLENGE 2 — SAME INSTRUMENT, DIFFERENT VISUAL VARIANTS

  Instruments come in different colors and sizes:

    "Kelly Clamp 14cm" (blue handle)
    "Kelly Clamp 14cm" (gold handle)
    "Kelly Clamp 20cm" (blue handle)

  RULES FOR GROUPING:

    Different COLOR   → SAME class
      Blue Kelly Clamp and Gold Kelly Clamp are visually
      different but functionally identical. Grouping them
      makes the detector robust to color variants.

    Different SIZE    → DIFFERENT class
      A 14cm clamp and a 20cm clamp are physically different
      instruments that a nurse must distinguish. They get
      separate training classes.

    Different SHAPE   → DIFFERENT class
      Curved vs straight, serrated vs smooth — these are
      distinct instruments with separate classes.

  HOW WE SOLVE IT:
  The normalizer keeps size/shape words but removes color words:
    Colors removed: blue, gold, black, silver, titanium, etc.
    Sizes kept:     14cm, 20cm, large, small, etc.
    Shapes kept:    curved, straight, angled, etc.


================================================================
THE ONE-COMMAND PIPELINE
================================================================

Instead of running 5 separate scripts, there is ONE command
that does everything:

    python run_pipeline.py --api-url http://localhost:3000

This single command:

  STEP 1 — COLLECT
    Pulls all instruments + kit definitions from the
    SurgicalInstruments API (images AND videos).

  STEP 2 — DEDUPLICATE
    Normalizes instrument names across kits.
    Merges duplicate names into single training classes.
    Different colors → same class.
    Different sizes → separate classes.
    Saves dedup_log.json for review.

  STEP 3 — ORGANIZE
    Downloads all still images.
    Downloads all video clips and EXTRACTS FRAMES from them
    (10 frames per video, with random jitter to avoid
    near-duplicate frames and maximize visual diversity).

  STEP 4 — LABEL (ground truth)
    Auto-generates YOLO detection labels from the images.
    For catalog images (instrument on neutral background):
    uses contour detection to find the instrument region.

  STEP 5 — SPLIT (balanced)
    Stratified shuffle ensuring EVERY instrument class
    appears in BOTH train AND test sets.
    Classes with < 3 images go to train only.
    Writes class_distribution.json for verification.

  STEP 6 — EXPORT
    Creates YOLO dataset structure:
      data/yolo_dataset/
        images/train/  images/val/  images/test/
        labels/train/  labels/val/  labels/test/
        data.yaml

  OUTPUT FILES:
    data/class_map.json             — all classes with IDs
    data/dedup_log.json             — which names were merged
    data/class_distribution.json    — per-class train/val/test counts
    data/kit_definitions.json       — kit data for count validation
    data/yolo_dataset/data.yaml     — ready for training

  OPTIONS:
    --train-ratio 0.8               — adjust split (default 0.70)
    --val-ratio 0.1                 — adjust val (default 0.15)
    --video-frames 15               — frames per video clip (default 10)
    --skip-sync                     — reuse existing downloads
    --seed 42                       — reproducible splits


================================================================
THE TWO TRAINING PATHS
================================================================

There are two model types we need to train, and they serve
different purposes:

  PATH A — INSTRUMENT DETECTOR (YOLOv8-seg)
  ──────────────────────────────────────────
  What:   Learns to find and classify instruments in a frame.
  Input:  One video frame (or catalog photo)
  Output: Bounding boxes + pixel masks + class labels
          ("this region is a Kelly clamp", "this is a sponge")
  Why:    Replaces manual keyframe annotation. Instead of a
          human clicking on instruments, the detector finds
          them automatically.
  Data:   Catalog images + video frames from SurgicalInstruments
          app, labeled by run_pipeline.py.
  Status: Training code ready (train/train_detector.py)

  PATH B — SAM3 TRACKING (propagation)
  ──────────────────────────────────────
  What:   Takes detector output (or manual prompts) and tracks
          instruments across the entire video.
  Input:  Initial detections on keyframes + full video
  Output: Per-frame masks with consistent identity across time
  Why:    Handles occlusion, movement, camera changes. Keeps
          "instrument #3" as the same physical object across
          1000+ frames.
  Status: Production-ready (zero-shot). Fine-tuning planned.

  HOW THEY WORK TOGETHER:

    Frame 0:  YOLOv8 detects → "3 sponges, 2 clamps, 1 scalpel"
                    │
                    ▼
    Frame 0:  SAM3 receives detections as prompts
                    │
                    ▼
    Frame 1-N: SAM3 propagates → tracks all 6 instruments
                    │
                    ▼
    Any frame: Instrument #4 disappears → LOST alert
                    │
                    ▼
    Kit check: Cross-reference count against kit catalog
               "Sheba Basic Set expects 42 → we see 41 → ALERT"


================================================================
WHAT THE TEAM NEEDS TO DO — STEP BY STEP
================================================================

──────────────────────────────────────────────────────────────
STEP 0: POPULATE THE CATALOG (SurgicalInstruments app)
──────────────────────────────────────────────────────────────

  Before anything else, the catalog must have data:

  [ ] Upload kit definitions (PDF or manual entry)
  [ ] For each instrument: upload images (photos from multiple
      angles, clean and used states) AND video clips
  [ ] Verify instrument names are consistent within each kit
  [ ] Check that each instrument has at least a few images

  The MORE images and videos per instrument, the BETTER the
  training data. Target: 10+ media items per instrument class.

  Access the catalog at: http://localhost:3000/dashboard.html

──────────────────────────────────────────────────────────────
STEP 1: RUN THE PIPELINE (automated — one command)
──────────────────────────────────────────────────────────────

    # Make sure the catalog app is running:
    cd SurgicalInstruments && node server.js

    # Run the full pipeline:
    python run_pipeline.py --api-url http://localhost:3000

  This pulls all data, deduplicates names, downloads images,
  extracts video frames, generates labels, creates balanced
  splits, and exports the YOLO dataset.

  Takes: 5-30 minutes depending on number of instruments.

──────────────────────────────────────────────────────────────
STEP 2: REVIEW THE OUTPUT
──────────────────────────────────────────────────────────────

  [ ] Check data/dedup_log.json
      Were the right names merged? Any wrong merges?

  [ ] Check data/class_distribution.json
      Does every class appear in train AND test?
      Are any classes severely underrepresented?

  [ ] Check data/class_map.json
      Are all instrument types present?
      Any missing classes?

  [ ] Spot-check data/yolo_dataset/images/train/
      Do the images look correct? Labels aligned?

──────────────────────────────────────────────────────────────
STEP 3: TRAIN THE DETECTOR
──────────────────────────────────────────────────────────────

    python train/train_detector.py \
      --data-yaml data/yolo_dataset/data.yaml \
      --epochs 50 \
      --imgsz 1024 \
      --batch-size 4

  Expected: ~15-20 hours on RTX 4090 / A100.

──────────────────────────────────────────────────────────────
STEP 4: EVALUATE
──────────────────────────────────────────────────────────────

    python eval/evaluate_detection.py \
      --predictions results.json \
      --ground-truth gt.json \
      --config config/config.yaml

    python eval/evaluate_tracking.py \
      --pred-dir data/predictions \
      --gt-dir data/ground_truth \
      --config config/config.yaml

──────────────────────────────────────────────────────────────
STEP 5: ADD OR VIDEO DATA (Phase 1A+)
──────────────────────────────────────────────────────────────

  Once we have OR recordings from Sheba:

  a) Place anonymized OR videos in data/videos/
     Naming: {site}_{specialty}_{case_id}.mp4

  b) Generate zero-shot annotations (sam3 env):
     python data_prep/generate_zero_shot.py \
       --config config/config.yaml \
       --video-dir data/videos \
       --output-dir data/annotations/zero_shot

  c) Human review in Label Studio (30-40 hours for 20 videos)

  d) Re-run pipeline with combined catalog + OR data

──────────────────────────────────────────────────────────────
STEP 6: INTEGRATE WITH PRODUCTION
──────────────────────────────────────────────────────────────

  Once the detector passes acceptance criteria:

  a) Export trained model weights
  b) YOLOv8 detector runs on first frame → finds instruments
  c) Detections become SAM3 prompts (replaces manual annotation)
  d) SAM3 propagates through video as before
  e) Cross-reference detected instruments against kit catalog
     from SurgicalInstruments app → verify count matches kit


================================================================
SYNC FROM CATALOG — DETAILED REFERENCE
================================================================

  In addition to run_pipeline.py, there is a standalone sync
  script for pulling catalog data without building a dataset:

    python data_prep/sync_from_catalog.py \
      --api-url http://localhost:3000 \
      --output-dir data

  This creates:
    data/taxonomy.json              — all instruments with families
    data/families.json              — family groupings + counts
    data/kits/                      — one JSON per surgical kit
    data/kit_instrument_counts.json — expected counts per kit
    data/detection_kit_mapping.json — instrument → kit lookup
    data/exemplars/                 — reference images per class

  To update config.yaml taxonomy from the catalog:
    python data_prep/sync_from_catalog.py \
      --api-url http://localhost:3000 \
      --output-dir data \
      --update-config

  WHAT THE CATALOG API PROVIDES:

    Endpoint                   What We Use It For
    ──────────────────────────────────────────────────────────
    GET /api/instruments       Names, families, manufacturers
                               → training labels
    GET /api/instruments/:id   Full-res images + videos
                               → exemplar library + training data
    GET /api/kit-catalogs      Kit definitions with instrument
                               lists → count ground truth
    GET /api/families          Family groupings → class hierarchy
    GET /api/export            Full data export for backup


================================================================
REALISTIC EXPECTATIONS — PHASE 1A (20 CASES)
================================================================

  With only 20 training cases (OR video), expect:

  Metric               Target     Phase 1A Estimate
  ──────────────────────────────────────────────────
  Detection AUC-ROC    >= 0.90    0.72-0.78
  Segmentation mIoU    >= 0.85    0.65-0.72
  Tracking HOTA        >= 0.80    depends on SAM3
  Count accuracy       >= 95%     ~80-85%

  This is EXPECTED. 20 cases is a baseline — targets are for
  Phase 1C (200-1000 cases). Each additional 30 cases improves
  AUC by ~0.10-0.15 points.

  NOTE: Training on catalog images ALONE (before any OR video)
  will give a reasonable starting detector for common instruments
  but will struggle with OR-specific challenges (lighting, blood,
  occlusion, crowded tables). OR video data is essential.

  Phase 1A success criteria (not final targets):
    [ ] Pipeline runs end-to-end without errors
    [ ] AUC > 0.75 on critical instruments (sponges, needles)
    [ ] Latency < 1s on OR hardware
    [ ] Identify which instrument classes need more data
